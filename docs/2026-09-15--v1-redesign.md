# fe-ai-workflow v1.0 重构方案

> 目标：从“靠 prompt 约束的重流程”升级为“基于原生 Skill 的轻流程 + 确定性门禁 + 只沉淀非推导知识”。
> 第 1～5 节是讨论稿，第 6 节是最终决定；两者冲突时以第 6 节和实际实现为准。

## 1. 现状诊断（基于 v0.8.1 仓库）

### A. 架构与分发

| # | 问题 | 证据 |
|---|------|------|
| A1 | 没有用上原生 Skill 机制：Claude Code / Codex / Cursor 都已支持 Agent Skills（SKILL.md，按 description 按需加载），但现在仍靠“每次对话必须加载元调度器”加路由表手工路由 | `CLAUDE.md` 启动规则、`workflow.mdc` 设置了 `alwaysApply: true` |
| A2 | 三端入口各自维护一份节点描述，内容重复，只能靠校验脚本保证一致 | CLAUDE.md 189 行、AGENTS.md 270 行、workflow.mdc 182 行；`validate-workflow.sh` 的 37 项检查都在校验这件事 |
| A3 | 元仓库自身的规则被注入到业务项目 | 注入到业务项目的 CLAUDE.md 里包含“本仓库为…”“Git Tag 发布规范”“AGENTS.md 与 SKILL.md 同步规则” |
| A4 | 分发时把 `skills/`、`references/` 覆盖式拷贝到业务项目根目录，污染业务仓库 | `sync-workflow.sh` 中的 `copy_path` |
| A5 | 仓库自身的 Claude Code 命令已损坏 | `.claude/commands/viktor/` 下 6 个软链接指向不存在的 `../../../commands/*.md`；另外 3 个是写着路径的纯文本文件 |

### B. 流程

| # | 问题 | 证据 |
|---|------|------|
| B1 | 所有任务都走同一套重流程：顺序不可跳过、每个节点都要确认、再加 1% 规则和反理由表，小改动的成本过高 | `using-fe-workflow` 的“强制规则”、各 SKILL 的反理由表 |
| B2 | “会话感知冷启动检测”在 5 个节点里各实现一遍，篇幅大且容易互相不一致 | 5 个 SKILL 各有一节前置步骤 |
| B3 | 同一个需求的产物分散在 specs / plans / contracts / reviews / adrs 五个目录，只能靠文件名拼接关联 | `docs/` 结构 |
| B4 | CONTRACT 把类型写在 `docs/contracts/` 下，与 `src` 中的真实类型形成两份副本，本身就会产生漂移 | `07-type-contract` |

### C. 知识沉淀

| # | 问题 |
|---|------|
| C1 | component-catalog、api-catalog 以及 project-context 中的组件、Hooks、路由清单，都是能从代码推导出来的知识。强 Agent 自己读代码就能得到，维护这些文档价值低、还容易过期 |
| C2 | CONTEXT、DIGEST 两个工具节点依附于这些活文档，价值随之下降 |
| C3 | 每个需求都强制写一份 ADR，真正的架构决策反而被淹没 |
| C4 | `references/` 约 840 行 React/Next 与测试规范，大部分是模型已经掌握的通用知识 |

### D. 执行与质量

| # | 问题 |
|---|------|
| D1 | 门禁依赖 prompt 约束（“禁止…”“必须…”），不是确定性的检查 |
| D2 | 由写代码的同一个上下文做 REVIEW，存在自我确认偏差；六轴加星级评分的报告模板很重，但真正需要处理的只有问题清单 |
| D3 | 强制所有代码注释使用中文，不一定符合项目约定 |

## 2. 设计原则

1. **原生优先**：以 Agent Skills 为唯一载体，三端入口文件只保留少量指针。
2. **按规模分档**：流程的重量由任务规模决定，而不是一刀切。
3. **确定性门禁**：能用脚本、hook 或测试检查的，不写成 prompt 规则。
4. **只沉淀非推导知识**：决策原因、踩过的坑、业务术语与约束；代码能说明的不再写文档。
5. **保留 TDD**：它是整套组合里价值最高的环节，继续作为核心。

## 3. 目标形态（讨论稿，已被第 6 节取代）

### 3.1 节点（9 个 → 6 个）

| 节点 | 变化 |
|------|------|
| `init` | 只生成项目段的 AGENTS.md（常用命令、目录约定、禁区、测试方式），不再生成组件清单 |
| `think` | 需求澄清，产出 spec 与验收标准；S 档跳过 |
| `plan` | 拆分任务；吸收 CONTRACT：接口和类型定义直接作为第一批任务写进 `src` |
| `code` | TDD 循环，要求提供真实运行的失败和通过证据 |
| `review` | 基于 diff 审查，只输出问题清单；优先在独立上下文（subagent 或新会话）中执行 |
| `ship` | 替代 doc：沉淀决策和踩坑（只在确实存在时），更新 CHANGELOG |

删除 `contract`、`context`、`digest`。

### 3.2 规模分档

| 档位 | 适用场景 | 流程 |
|------|---------|------|
| S | bug 修复、小改动 | code → review |
| M | 常规需求 | think（精简版）→ code → review → ship |
| L | 跨模块或新功能 | think → plan → code → review → ship |

档位由 AI 判断，并在开始时声明，用户可以改。

### 3.3 产物目录

```
docs/
├── changes/<YYYY-MM-DD>--<feature>/   # 按需求组织
│   ├── spec.md      # frontmatter 中的 status 字段作为唯一状态源，替代冷启动检测
│   ├── tasks.md
│   └── review.md
└── knowledge/                         # 只放非推导知识
    ├── decisions.md
    ├── pitfalls.md
    └── glossary.md
```

### 3.4 分发

- `skills/` 是唯一真相源，由安装脚本分别装到 `.claude/skills/`、`.agents/skills/`、`.cursor/skills/`（具体路径需按三端当前文档实测确认）。
- 注入的入口段控制在约 30 行以内，并与元仓库自身的 CLAUDE.md 分离。
- 可选：以 Claude Code plugin 的形式分发。

### 3.5 门禁

- 统一定义 `lint`、`typecheck`、`test` 三个检查命令，由 `init` 写入 AGENTS.md。
- Claude Code 通过 hooks 执行，其他端通过脚本或 CI 执行。
- `validate-workflow.sh` 改为校验 SKILL frontmatter 和入口指针。

## 4. 验收方式

- 用 todolist demo 端到端跑通 S、M、L 三个档位，覆盖 Claude Code 和 Codex。
- 对比 v0.8.1：记录常驻上下文的行数、各档位的交互轮次、产物文件数。

## 5. 待确认决策

1. 是否采用 S/M/L 分档？
2. 是否删除 contract、context、digest 三个节点？
3. 产物目录改为 `changes/` 加 `knowledge/`（这是破坏性变更，发布为 v1.0.0）？
4. 分发方式：安装到三端原生 skills 目录，还是以 plugin 为主？
5. 命令前缀是否继续使用 `viktor:`？

## 6. 最终决定（2026-09-15）

1. 采用 S/M/L 分档。
2. 节点精简为 5 个：init / plan / code / review / ship。think 与 plan 合并；contract 并入 plan/code；删除 context、digest。
3. 产物目录改为 `changes/` + `knowledge/`，发布 v1.0.0；v0 产物直接删除。
4. 分发到 `.claude/skills`（Claude Code）和 `.agents/skills`（Codex、Cursor）；技能名三端一致，调用前缀按端区分。
5. CLAUDE.md 只保留 `@AGENTS.md`，入口内容集中在 AGENTS.md。
6. hooks 门禁纳入 v1.0。
7. 不再依赖 superpowers。
8. 独立审查（docs/2026-09-15--v1-review.md）后的补充决定：检查命令改为 AGENTS.md 中的 `viktor-checks` 块；hook 使用 `$CLAUDE_PROJECT_DIR`、改动指纹、最多拦截 3 次；`--migrate` 只删精确名单；S/M/L 改用可观察判据；Codex hooks 待 demo 阶段实测后再决定是否接入。
