# 前后端通用 + 验收证据规格

> 与 Codex 三轮交叉评审后定稿。目标：同一套工作流支持前端（Vue / React）与后端（Java 为主）仓库，各自独立调用；核心七节点、卡片、状态机、快照、知识库不动。不引入 profiles，差异以条件规则写进节点与提示词。

## 1. 原则

- 可从代码推导的知识不写进工作流（构建工具、测试框架、迁移工具由模型读仓库判断）。
- 执行边界与通过条件必须明确，不靠模型临场决定。
- 允许降低执行方式，不允许降低通过标准。

## 2. 关键 AC 与最低证据

- 默认关键（plan 不标也算，S 档自动生成的 AC 同样适用）：数据写入 / 迁移 / 删除、权限与租户隔离、对外接口或消息契约、资金与计费、幂等与重试。
- plan 可显式标 `关键` / `非关键`；降为非关键必须写理由。check 核对理由与实际行为是否相符，理由错误或遗漏风险才推翻，不因命中默认类别就推翻。
- 关键只意味着缺证据不放行；不意味着必须跑完整集成测试或升 L 档。
- check 按每条 AC 要证明的行为选最小充分证据：纯计算 → 单测；持久化行为 → 相关数据库语义（mock / 内存库不默认等价）；鉴权 → 正反例；异步 → 观察最终结果。没有固定的证据阶梯。

## 3. 验收结果对应表

| 结果 | 含义 | 退出码 | 修业务代码 | 写 verified.check | 可收尾 | 续接 |
|---|---|---|---|---|---|---|
| pass | 全部 AC 有充分证据 | 0 | 否 | 是 | 是 | 指纹与输入摘要一致则跳过 |
| manual | 仅非关键 AC 待人工 | 0 | 否 | 是（含 `pending: [AC…]`，含义=满足放行条件） | 是，报告单列未验项 | 同上 |
| failed | 观察到行为错误 | 1 | 是 | 否 | 否 | 修完先复审 review 再重验 |
| blocked | 关键 AC 证据缺失（环境不可用 / 证据不足） | 4 | 否 | 否 | 否 | 见 §5 |
| error | 命令无法执行 | 2 | 否 | 否 | 否 | 见 §5 |

混合结果优先级：failed > blocked > error > manual > pass。观察到任一业务失败即 failed，其他 AC 的阻塞在报告里保留。

review：pass → 0 写 verified.review；blocked（有 BLOCKING）→ 1 修代码；error → 2。

## 4. 命令按用途区分

`viktor-checks` 键：`typecheck` / `lint` / `test`（快速，hook 用）/ `verify`（完整验收，check 用，可选）/ `dev`、`e2e`（可选）。另加"运行前提"节：环境入口与就绪条件（工作目录固定为 AGENTS.md 所在目录，子模块写进命令）、清理方式、时间预算；不记录密钥。

- hook 只跑 typecheck / lint / test。
- review 重跑与改动相关的测试：优先项目已有的测试选择机制，按实际模块依赖确认范围；判断不了就全量；报告写选择依据与未覆盖范围。拿不到 hook 证据时补跑缺证据的 typecheck 与 lint，证据必须对应当前代码。
- check 跑 verify 或按 AC 挑选；未验证的命令可以执行，只是它自身不构成通过证据。
- 允许验证所需的编译；禁止与验证无关的打包发布。

## 5. 续接

1. 算代码指纹，对 `verified.review`：不一致 → 先 review（复审模式）。
2. 一致 → 算验收输入摘要（AC 列表 + 证据要求 + 本轮运行配置的哈希）对 `verified.inputs`：不一致 → 重跑 check。
3. 都一致 → 按 stage 继续。blocked / error 的节点即使指纹一致也重跑（环境恢复后直接重验 check，但仍先经过第 1 步）。

## 6. init 与预检

- init：模型推导命令（优先读 CI 配置、wrapper、README），实跑一次核对：test 看执行数 > 0、跳过数、目标模块；typecheck / lint 看退出码；verify 允许不跑。每条记录 `已验证` 或 `已发现未验证（原因）`。执行前确认目标为测试环境。不安装依赖、不启动服务、不改造命令。单仓库多模块在此把模块参数写进命令。
- 预检（不修改项目配置）：节点发现无项目配置时，主会话推导本轮配置写入 plan.md 独立一节 `## 本轮运行配置`（命令、目录、前提、来源），不碰 AGENTS.md 与 settings.json，卡片备注建议 /viktor-init。
- 派单前主会话解析本轮实际配置显式传给子进程（spawn 参数），子进程不自行读配置。
- 优先级：项目配置是权威，出现即取代临时配置，记录差异并作废依赖旧配置的验收证据；只在新配置本身有执行歧义时提问。

## 7. 资源与进程

- spawn 起独立进程组：有 perl 用 `setpgrp`，否则按进程树递归终止。正常、失败、超时都执行清理。
- 子进程**不自行创建容器**来验证；只登记自己直接创建的资源（临时目录、后台 dev 的 pid），以本轮 run_id 命名并**创建即登记**到 `.check.resources`（只存标识）。清理只处理能按 run_id / 进程组识别的资源，其余只报告；对已有服务只断开本轮连接。
- 测试框架内部创建的容器（Testcontainers）由框架自己回收（ryuk），子进程在 check.md 说明即可。spawn 超时兜底：有 docker 时，带 `org.testcontainers.sessionId` 标签、且本轮开始时还不存在的容器一律 `rm -f`，本轮之前已有的只报告。（2026-09-18 验证修复 F5）

## 8. 提示词中立化与后端附加项

- 去掉"前端项目"、"不跑 build"、"类型写进 src"等假设；接口契约写进代码里对应位置。
- review 按 diff 触发：迁移 → 迁移安全与恢复策略；鉴权 → 对象 / 租户级授权正反例；重试或消息 → 幂等；外部调用 → 超时与副作用一致性；查询 → 分页边界。
- TDD 例外统一为"无法形成有意义的行为 RED 时提供替代验证并说明理由"；环境不可用不是免测理由。
- 分档按兼容性、数据影响、恢复成本判断。

## 9. 验证场景

Spring Boot 多模块（Maven）S / M 各一次；Vue 回归一次；定向：关键 AC 缺数据库 → blocked 且不改代码；非关键人工项 → manual 收尾且报告单列；测试全部跳过 → 不得通过；超时后资源清理；未初始化时子进程使用临时配置；环境恢复后先 review 再 check；缺上游构建产物的测试选择。Gradle 本轮不声明支持。
