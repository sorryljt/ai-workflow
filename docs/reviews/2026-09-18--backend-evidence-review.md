- 基线：v1.0.1（9bc87c4）

- 工作区开始时干净。本次只新增本报告，没有修改实现或仓库测试。

## 结论

建议修复下列问题后再发布。五态退出码、提示词中立化和超时进程组终止已有实现，现有测试全部通过；但正常结束后的进程清理、运行前提传递和 S 档验收摘要存在可复现缺陷。命令用途分离和 plan 最低证据要求尚未完整落实到作为真相源的 SKILL.md。

这不是对整个方案的否定，也不意味着后端已实测失败；当前证据支持的是“脚本及规则接线尚有缺口”，不能据此宣称 Java 项目已经验证可用。

## Findings（按优先级）

### R1 · P1：运行前提没有按 init 的产物格式传入子进程

位置：scripts/viktor-spawn.sh:97–100；skills/viktor-init/SKILL.md:27；skills/viktor-review/SKILL.md:19；skills/viktor-check/SKILL.md:17。

问题：init 模板生成 `- 运行前提：…`，spawn 只解析 `### 运行前提` 节。因此按正式 init 模板产生的数据库等环境要求会被丢弃。即使改用三级标题，解析末尾的 `sed '$d'` 也会在该节位于文件末尾时删掉最后一条前提。临时配置路径则要求派单器只传“里的块”，没有明确包含块外的执行目录和环境说明。

复现：临时仓库 AGENTS.md 含 `- 运行前提：ONLY_TEST_DB` 和合法 checks 块，生成的 `.check.prompt.md` 不含该标记；改成文件最后一个 `### 运行前提` 节，最后一行 `ONLY_LAST_DB` 仍未进入提示词。

后果：子进程在缺少执行目录、数据库前提或环境说明的情况下运行，容易错误阻塞或在错误上下文中验证。

建议：统一 init、临时配置、spawn 的格式；传入完整运行配置；按下一标题或 EOF 结束解析，不无条件删除最后一行。为两种配置来源和末节场景补测试。

### R2 · P1：合法 pid 记录永远无法清理，正常结束后遗留进程

位置：scripts/viktor-spawn.sh:149–168。

问题：所有资源在分类前都要求 id 包含 RUN_ID。合法 `pid:85645` 的 id 只有数字，不可能包含日期和脚本 PID 组成的 RUN_ID，因此永远无法进入 pid 清理分支。进程组终止又只发生在超时路径，正常或异常退出不会终止剩余的同组进程。

复现：假的 claude 启动 `sleep 60`、写入 `pid:$!`、产生本轮 pass 报告并退出。spawn 返回 0；随后检查到 sleep 仍存活，stderr 为“未处理（不含本轮 run_id）：pid:85645”。复现结束后已手动终止该测试进程。

后果：服务占用端口、后台测试进程遗留；只测试超时路径会漏掉此问题。

建议：进程归属通过本轮进程组或其他可靠身份信息判断，不要求数字 PID 包含 run_id；正常、失败、超时都处理本轮残留进程。不要简单删除归属检查后无条件 kill 清单里的 PID。

### R3 · P1：S 档合法的简版 AC 不进入验收输入摘要

位置：scripts/viktor-spawn.sh:42–46；skills/viktor-code/SKILL.md:11。

问题：摘要只提取 `## 验收标准` 和 `## 本轮运行配置` 两个标题下的内容。S 档要求正文只有问题描述和一条 AC，没有要求生成 `## 验收标准`；check 也接受 S 档问题描述作为输入。

复现：plan 正文为“问题：示例 / AC-1：旧行为”，将 AC 改成“新行为，要求真实数据库”后，两次摘要均为 `b47b1dd2e1a6`。

后果：代码未变、仅修改 S 档验收行为或最低证据时，旧验收输入摘要仍匹配，续接可能复用不适用的验收结果。

建议：统一 S/M/L 的 AC 标题协议并兼容已有简版计划，或让摘要明确覆盖 S 档实际验收输入。找不到有效 AC 不应静默返回一个可复用的成功摘要。

### R4 · P2：命令用途分离尚未进入实际工作流规则

位置：skills/viktor-init/SKILL.md:12–17、30–35、45–50；skills/viktor-code/SKILL.md:42。

问题：规格约定 `test` 为快速检查、`verify` 为完整验收，但 init 没有发现/记录 verify 的要求，也未定义 test 必须适合 hook。code 仍要求完整运行 checks 中所有命令，没有排除 dev 和慢验收。仓库 skills/prompts 中未形成 verify 的用途约束。

触发：Java 项目已有快速单测和需要数据库的完整验收入口。按当前 init 规则，模型仍可能把全量测试放入 test；之后 hook、code、review 重复执行，300 秒 hook 和 480 秒 spawn 的原有预算仍适用。

后果：方案要解决的慢测试重复执行并未解决；把 verify 手动加入块中也不能阻止 code 按原规则重跑。

建议：把用途约束落实到 init 探测与模板、code 完成条件和 check 输入；明确 dev 是启动入口，不是需要等待退出的检查。此项属于已确认功能未完成，部分冲突代码是 v1.0.1 遗留，不全部是本次新增回归。

### R5 · P2：plan 中没有关键 AC 与最低证据的生成规则

位置：skills/viktor-plan/SKILL.md:88–90、112–116；skills/viktor-code/SKILL.md:11。

问题：plan 的 AC 模板仍只有行为描述，写作要求没有关键默认规则、最低证据或降级理由。code 新增“按 viktor-plan 的规则写一句证据要求”，但对应规则不存在。具体分类仅写在 check 提示词和设计文档中，后者不是节点的必读输入。

后果：M/L 计划确认时，用户仍看不到最终验收的证据门槛；直到 check 才决定需要真实数据库或授权反例。S 档也存在悬空引用。

建议：在 plan 的真相源中补齐 AC 格式和最低证据要求，并保证 S 档引用到实际存在的规则。可共享一段规则，避免三份独立维护。

### R6 · P2：缺配置时子进程仍被明确要求自行探测

位置：scripts/viktor-spawn.sh:102。

问题：新增兜底提示为“能从仓库推断就用推断的命令”，与确认的“主会话预检、子进程不兜底”相反。直接调用 review/check、缺少临时配置或主会话漏传 --checks 时会进入此分支。

后果：独立进程执行主会话没有解析和传入的命令；失败原因和配置来源变得不确定。当前测试只断言出现“未找到检查命令”，没有验证应停止执行。

建议：无有效配置时返回配置错误，主会话补齐后再派单；若有意保留兼容模式，应明确显式启用，不能作为默认行为。

## 续接规则中的既有冲突（不计入新增缺陷数量）

skills/viktor-flow/SKILL.md:29–32 对所有续接任务先比较 verified.review，缺少指纹则进入 review。但 draft、刚 confirmed 和 code 未完成的任务本来没有审查指纹，应先按同文件 39–42 行恢复 plan/code。该冲突在 v1.0.1 的指纹续接规则中已有，本次改为更明确的顺序后仍未解决。

此外，第 54 行仍把缺 checks 作为必须停止并建议 init 的条件，与新增 plan/code 预检冲突。建议先按当前阶段确定是否已经进入审查/验收，再应用指纹失效逻辑；缺 checks 时明确进入预检或报告无法形成配置。

这两点是静态规则冲突，没有通过真实模型会话复现，不将其表述为已观察到的跳过编码事件。
